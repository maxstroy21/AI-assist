## 3. Выявленные противоречия и их разрешение

Это самая важная часть этапа: исходные пожелания местами конфликтуют, и каждое
разрешение — архитектурное решение.

### П-1. «AI First» ↔ надёжность напоминаний и планировщика

**Конфликт.** «Любое действие через LLM» — но напоминание в 9:00 обязано сработать в 9:00,
даже если модель выгружена, галлюцинирует или медленна. Локальные модели ошибаются чаще облачных.

**Решение.** Разделяем **интерпретацию** и **исполнение**:
- LLM отвечает за понимание («каждый понедельник в 9» → RRULE, «напомни после отпуска» → триггер-условие);
- исполнение (срабатывание по расписанию, доставка, retry) — детерминированный код без LLM.

AI First применяем к принятию решений, а не к механике. Это же правило распространяется
на файловые операции: LLM решает *что* сделать, детерминированный инструмент *делает*.

### П-2. «Local First» ↔ качество моделей

**Конфликт.** Локальные модели (7–70B) слабее облачных в tool calling и длинном контексте.
Требования (агентность, извлечение памяти, объединение задач) чувствительны к качеству модели.

**Решение.**
- Архитектура не предполагает конкретного качества модели: сложные цепочки разбиваются на простые шаги с маленькими промптами (лучше 5 простых вызовов, чем 1 сложный);
- structured output валидируется Pydantic-схемами с автоматическим retry при невалидном ответе;
- LLM Gateway позволяет назначать **разные модели на разные роли** (диалог / извлечение памяти / эмбеддинги / классификация) — и, опционально и явно, облачную модель на отдельные роли, если пользователь когда-нибудь захочет. По умолчанию — всё локально.

### П-3. «Agentic» ↔ безопасность файловых операций

**Конфликт.** Автономный агент с правом перемещать/архивировать файлы может необратимо испортить файловую систему из-за одной галлюцинации.

**Решение.** Трёхуровневая модель риска инструментов (FR-9.5):
- `read` — свободно;
- `write` (создание нового, перемещение с журналом) — свободно, но с undo-журналом;
- `destructive` (удаление, перезапись, массовые операции) — только после явного подтверждения в чате.

Плюс: файловые операции работают только внутри whitelisted корневых папок.

### П-4. «Модульность/микросервисность» ↔ одна личная машина

**Конфликт.** «Не монолит, слабая связанность» наивно читается как микросервисы. Но 10 процессов, брокер сообщений и Docker-оркестрация на личном Windows-ПК — это операционный кошмар для одного человека и прямое нарушение «максимальной автономности».

**Решение.** **Модульный монолит**: один процесс, жёсткие границы модулей через интерфейсы и событийную шину in-process. Любой модуль спроектирован так, что его можно вынести в отдельный процесс (MCP-сервер), когда это реально понадобится. Подробное сравнение — в [02-architecture.md](02-architecture.md).

### П-5. «Всё индексировать» ↔ ресурсы машины

**Конфликт.** Постоянная фоновая индексация + LLM + эмбеддинги конкурируют за GPU/CPU/RAM с работой пользователя и с самим диалогом.

**Решение.**
- Индексация — инкрементальная (watchdog по FS-событиям + периодический полный скан), с низким приоритетом;
- эмбеддинг-модель маленькая и отдельная от чат-модели;
- тяжёлые работы (полная переиндексация, OCR-пакеты, консолидация памяти) — по расписанию в «тихие часы» (настраивается);
- очередь индексации приостанавливается, когда идёт активный диалог.

### П-6. Память «помнит всё» ↔ ограниченный контекст локальной модели

**Конфликт.** Нельзя положить «всю память» в промпт: контекст локальной модели 8–32K токенов, и чем длиннее промпт, тем хуже модель следует инструкциям.

**Решение.** Память — это **retrieval-задача**, а не «большой промпт»: в контекст попадает только релевантная выжимка (предпочтения — всегда, остальное — по семантическому поиску относительно текущего запроса). Плюс фоновая консолидация: диалоги → суммаризация → структурированные факты.

### П-7. «Задай вопросы» ↔ «работай автономно»

**Решение.** Все вопросы, без ответа на которые проектирование остановилось бы, разрешены разумными допущениями (см. §5) и вынесены в открытые вопросы (§4). Ни одно из этих допущений не ломает архитектуру при другом ответе — меняется только конфигурация или один адаптер.

### 4.1. Адаптация под ответ Q-1 (Ollama + mistral 7B)

Что это меняет (и что — нет):

- **Архитектура не меняется.** Ollama — самый удобный из семи рантаймов: нативный OpenAI-совместимый API, автозагрузка/выгрузка моделей, `keep_alive` управляется параметром запроса. LLM Gateway работает с ним без адаптеров.
- **mistral:7b (v0.3) поддерживает нативный function calling** через Ollama — режим tool calling в agent loop будет работать напрямую; JSON-fallback остаётся страховкой на случай нестабильного выбора инструментов у 7B-модели.
- ⚠️ **Русский язык — слабое место Mistral 7B**: модель заметно хуже пишет и рассуждает по-русски, чем сопоставимые по размеру **qwen2.5:7b-instruct** или **llama3.1:8b**. Так как основной язык общения — русский, рекомендация к Sprint 1: `ollama pull qwen2.5:7b-instruct` и сравнить на своих задачах; mistral оставить как альтернативу в конфиге. Это ровно тот случай, ради которого роли моделей вынесены в `models.yaml` — переключение без кода.
- **Эмбеддинги — не через чат-модель**: как и заложено, in-process `bge-m3` (мультиязычный), либо `ollama pull nomic-embed-text` как вариант через тот же Ollama API. Решение — при Sprint 4.
- **Эксплуатационная заметка (Windows):** Ollama при установке регистрируется как фоновый сервис и уже слушает `127.0.0.1:11434`; запускать `ollama serve` вручную не нужно (даст `bind: Only one usage of each socket address` — это не сбой, а признак уже работающего сервера). Наш сервис-режим (Sprint 1) будет лишь проверять доступность API при старте и ждать/поднимать Ollama при необходимости.
- Открытым остаётся **Q-2 (железо: GPU/VRAM/RAM)** — от него зависит, потянет ли машина модель покрупнее (14B) для роли `chat` и сколько параллелизма давать индексатору.

Пример `config/models.yaml` под текущую установку:

```yaml
runtimes:
  ollama:
    kind: openai_compatible
    base_url: http://localhost:11434/v1
    api_key: ollama          # заглушка, Ollama не проверяет

roles:
  # 2026-07-17: среда проверена — qwen2.5:7b-instruct скачан и назначен основной
  # моделью диалога (лучший русский среди 7B); mistral остаётся запасным вариантом.
  chat:       { runtime: ollama, model: "qwen2.5:7b-instruct",
                temperature: 0.7, keep_alive: 60m }
  extraction: { runtime: ollama, model: "qwen2.5:3b-instruct", temperature: 0.0 }  # ollama pull qwen2.5:3b-instruct
  summarize:  { runtime: ollama, model: "qwen2.5:3b-instruct", temperature: 0.3 }
  embedding:  { runtime: inprocess, model: BAAI/bge-m3 }
  rerank:     { runtime: inprocess, model: BAAI/bge-reranker-v2-m3 }
  stt:        { runtime: inprocess, model: faster-whisper-small }
```

### 4.2. Адаптация под ответ Q-2 (CPU-only: i7-1165G7, 16 ГБ RAM)

Дискретного GPU нет; Intel Iris Xe Ollama не ускоряет (поддерживаются CUDA/ROCm/Metal) —
**инференс идёт на CPU**. Это не блокер: 7B-модель в квантовании Q4 работает на этом
процессоре со скоростью ~3–6 токенов/с генерации. Но из этого следуют конкретные решения:

**Ограничения железа:**

| Ресурс | Факт | Следствие |
|--------|------|-----------|
| CPU 4C/8T | Генерация 7B Q4 ≈ 3–6 т/с; обработка промпта ≈ 15–40 т/с | Модели >7–8B исключены; **короткие промпты — главный рычаг скорости** (2000 токенов промпта = ~1 мин до первого токена!) |
| RAM 16 ГБ | 7B Q4 ≈ 4.5 ГБ + эмбеддер + Qdrant + ОС | Одна LLM резидентно (`keep_alive: 60m` — можно держать), 14B не влезает комфортно даже без учёта скорости |
| iGPU | Не используется | Опциональный эксперимент: сборка Ollama от Intel (**ipex-llm**) умеет Iris Xe — ускорение ~1.5–2×; отложить в backlog, не усложнять старт |
| SSD ~113 ГБ свободно | Модели ~5–10 ГБ + индекс | Достаточно; следить при росте корпуса (OCR-кэш, бэкапы → retention) |

**Пересмотр ролей моделей (обновляет пример из §4.1):**

| Роль | Было (по умолчанию) | Стало (CPU-only) | Почему |
|------|--------------------|------------------|--------|
| `chat` | 7B–14B | **qwen2.5:7b-instruct** (Q4), mistral как запасной | Максимум качества, который тянет CPU; лучший русский среди 7B |
| `extraction` | = chat | **qwen2.5:3b-instruct** | Структурные задачи (даты, факты) не требуют 7B; в 2–3 раза быстрее — а это фоновые задачи после каждого сообщения |
| `summarize` | = chat | qwen2.5:3b-instruct | То же |
| `embedding` | bge-m3 (570M) | **intfloat/multilingual-e5-small** (118M); bge-m3 — опция качества | На CPU bge-m3 сделает индексацию большого корпуса многочасовой; e5-small — хороший мультиязычный компромисс |
| `rerank` | bge-reranker-v2-m3 | **выключен по умолчанию** | +секунды на каждый поиск на CPU; включать точечно, если качество retrieval не устроит |
| `stt` | faster-whisper small | faster-whisper **small int8** | На CPU транскрибирует голосовое ~в реальном времени |

**Архитектурные следствия (уточнение, не изменение):**

1. **Бюджет промпта — жёсткий**: Context Builder целится в ≤ 1200–1500 токенов промпта для обычного диалога (system ~200, память ~300, история ~500, RAG-фрагменты — только при реальном поиске). Фильтрация набора инструментов по контексту (§5.1 архитектуры) становится обязательной, а не желательной: ≤ 6–8 тулов в промпте.
2. **Скорректированные целевые NFR** (правки в §2): начало ответа простого диалога ≤ 5 с; RAG-ответ ≤ 30–45 с полностью. Streaming обязателен — субъективно ответ «живой» сразу.
3. **Индексация**: 1–2 воркера, только в паузах диалога и тихие часы; первичная индексация корпуса — ночной процесс (возможно, не одна ночь — это нормально, идёт инкрементально).
4. **`OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_LOADED_MODELS=1`** — одна модель в RAM; переключение chat↔extraction дешёвое (3B грузится секунды). Фоновые LLM-задачи (извлечение памяти) — строго в очередь, никогда параллельно с диалогом.
5. **Утренняя сводка и консолидация** — идеальные кандидаты на ночные часы: пусть медленно, зато к утру готово.
6. Если через полгода захочется большего — путь апгрейда прозрачен: любой ПК/мини-ПК с 12–16 ГБ VRAM, перенос `data/` + конфиг, всё остальное без изменений (NFR-9).
