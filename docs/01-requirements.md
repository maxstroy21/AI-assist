# Этап 1. Требования, противоречия, решения

Этот документ фиксирует, **что** система должна делать, **какие ограничения** на неё наложены,
где исходные пожелания **противоречат друг другу** и какие решения приняты.

## 2. Нефункциональные требования

| ID | Требование | Целевое значение |
|----|------------|------------------|
| NFR-1 | Горизонт жизни проекта | ≥ 3–5 лет развития без переписывания ядра |
| NFR-2 | Платформа | Windows — основная машина; код кроссплатформенный (Linux/macOS), **без жёсткой зависимости от Docker** |
| NFR-3 | Латентность простого ответа | ≤ 2–3 с до начала ответа (streaming) при адекватной локальной модели |
| NFR-4 | Латентность RAG-ответа | ≤ 10 с на типовой вопрос по базе документов |
| NFR-5 | Объём корпуса | До ~100 тыс. документов / ~1 млн чанков без смены архитектуры |
| NFR-6 | Автономность | Запуск как сервис при старте ОС, авто-восстановление после сбоя |
| NFR-7 | Наблюдаемость | Структурированные логи, трассировка каждого запроса (request id через все сервисы) |
| NFR-8 | Тестируемость | Каждый модуль тестируется изолированно; LLM подменяется фейком в тестах |
| NFR-9 | Замена модели | Смена LLM/эмбеддера — операция конфигурации + фоновая переиндексация, не код |

## 3. Выявленные противоречия и их разрешение

Это самая важная часть этапа: исходные пожелания местами конфликтуют, и каждое
разрешение — архитектурное решение.

### П-1. «AI First» ↔ надёжность напоминаний и планировщика

**Конфликт.** «Любое действие через LLM» — но напоминание в 9:00 обязано сработать в 9:00,
даже если модель выгружена, галлюцинирует или медленна. Локальные модели ошибаются чаще облачных.

**Решение.** Разделяем **интерпретацию** и **исполнение**:
- LLM отвечает за понимание («каждый понедельник в 9» → RRULE, «напомни после отпуска» → триггер-условие);
- исполнение (срабатывание по расписанию, доставка, retry) — детерминированный код без LLM.

AI First применяем к принятию решений, а не к механике. Это же правило распространяется
на файловые операции: LLM решает *что* сделать, детерминированный инструмент *делает*.

### П-2. «Local First» ↔ качество моделей

**Конфликт.** Локальные модели (7–70B) слабее облачных в tool calling и длинном контексте.
Требования (агентность, извлечение памяти, объединение задач) чувствительны к качеству модели.

**Решение.**
- Архитектура не предполагает конкретного качества модели: сложные цепочки разбиваются на простые шаги с маленькими промптами (лучше 5 простых вызовов, чем 1 сложный);
- structured output валидируется Pydantic-схемами с автоматическим retry при невалидном ответе;
- LLM Gateway позволяет назначать **разные модели на разные роли** (диалог / извлечение памяти / эмбеддинги / классификация) — и, опционально и явно, облачную модель на отдельные роли, если пользователь когда-нибудь захочет. По умолчанию — всё локально.

### П-3. «Agentic» ↔ безопасность файловых операций

**Конфликт.** Автономный агент с правом перемещать/архивировать файлы может необратимо испортить файловую систему из-за одной галлюцинации.

**Решение.** Трёхуровневая модель риска инструментов (FR-9.5):
- `read` — свободно;
- `write` (создание нового, перемещение с журналом) — свободно, но с undo-журналом;
- `destructive` (удаление, перезапись, массовые операции) — только после явного подтверждения в чате.

Плюс: файловые операции работают только внутри whitelisted корневых папок.

### П-4. «Модульность/микросервисность» ↔ одна личная машина

**Конфликт.** «Не монолит, слабая связанность» наивно читается как микросервисы. Но 10 процессов, брокер сообщений и Docker-оркестрация на личном Windows-ПК — это операционный кошмар для одного человека и прямое нарушение «максимальной автономности».

**Решение.** **Модульный монолит**: один процесс, жёсткие границы модулей через интерфейсы и событийную шину in-process. Любой модуль спроектирован так, что его можно вынести в отдельный процесс (MCP-сервер), когда это реально понадобится. Подробное сравнение — в [02-architecture.md](02-architecture.md).

### П-5. «Всё индексировать» ↔ ресурсы машины

**Конфликт.** Постоянная фоновая индексация + LLM + эмбеддинги конкурируют за GPU/CPU/RAM с работой пользователя и с самим диалогом.

**Решение.**
- Индексация — инкрементальная (watchdog по FS-событиям + периодический полный скан), с низким приоритетом;
- эмбеддинг-модель маленькая и отдельная от чат-модели;
- тяжёлые работы (полная переиндексация, OCR-пакеты, консолидация памяти) — по расписанию в «тихие часы» (настраивается);
- очередь индексации приостанавливается, когда идёт активный диалог.

### П-6. Память «помнит всё» ↔ ограниченный контекст локальной модели

**Конфликт.** Нельзя положить «всю память» в промпт: контекст локальной модели 8–32K токенов, и чем длиннее промпт, тем хуже модель следует инструкциям.

**Решение.** Память — это **retrieval-задача**, а не «большой промпт»: в контекст попадает только релевантная выжимка (предпочтения — всегда, остальное — по семантическому поиску относительно текущего запроса). Плюс фоновая консолидация: диалоги → суммаризация → структурированные факты.

### П-7. «Задай вопросы» ↔ «работай автономно»

**Решение.** Все вопросы, без ответа на которые проектирование остановилось бы, разрешены разумными допущениями (см. §5) и вынесены в открытые вопросы (§4). Ни одно из этих допущений не ломает архитектуру при другом ответе — меняется только конфигурация или один адаптер.

## 5. Принятые допущения (по умолчанию, пока нет ответов)

| # | Допущение | Обоснование |
|---|-----------|-------------|
| A-1 | Рантайм LLM предоставляет OpenAI-совместимый HTTP API на localhost | Все 7 перечисленных рантаймов либо имеют его нативно (Ollama, LM Studio, vLLM, llama.cpp-server, Jan), либо ставятся за прокси |
